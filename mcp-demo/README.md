# MCP demo: `score_lead` as an MCP tool

> **EXPERIMENT.** This folder is a side-by-side demo, not part of the live
> pipeline in `src/lead_intelligence/`. Nothing there was modified.

The Qualification Agent today gets `score_lead` through Claude's direct tool
use: a hand-written `SCORE_LEAD_TOOL` dict is sent with every request and the
agent executes the call in-process. This demo exposes the **same function**
(imported from `src/lead_intelligence/scoring.py`, not copied) as a tool on a
local MCP server built with the official SDK's FastMCP.

## Files

| File | Purpose |
|---|---|
| `server.py` | FastMCP server, one tool: `score_lead` (loose `lead: object` schema, same description as the direct version) |
| `measure_tokens.py` | Counts the tool definition's tokens, direct vs MCP, and writes `results.json` (needs `ANTHROPIC_API_KEY`) |
| `tests/` | pytest tests that call the tool directly; no Claude Desktop or API key needed |
| `requirements.txt` | Extra dependencies for this folder only (`mcp` is pinned) |

## How to run

From the repo root, in a virtualenv:

```bash
pip install -r requirements.txt          # repo-wide deps (xgboost, shap, anthropic, ...)
pip install -r mcp-demo/requirements.txt # mcp (pinned, <2) and pytest

# tests (no API key needed)
python -m pytest mcp-demo

# start the server on stdio (normally launched by an MCP client, not by hand)
python mcp-demo/server.py

# measure tool-definition size (needs the key in your environment)
export ANTHROPIC_API_KEY=...             # Windows PowerShell: $env:ANTHROPIC_API_KEY="..."
python mcp-demo/measure_tokens.py        # writes mcp-demo/results.json
```

`mcp` is pinned to a 1.x release because mcp 2.x renamed `FastMCP` to
`MCPServer`.

## Claude Desktop config

Add to `claude_desktop_config.json` (placeholder paths, replace with yours;
note the escaped backslashes):

```json
{
  "mcpServers": {
    "coffra-lead-scoring": {
      "command": "C:\\path\\to\\venv\\Scripts\\python.exe",
      "args": ["C:\\path\\to\\coffra-marketing-automation\\mcp-demo\\server.py"]
    }
  }
}
```

Use the Python from the virtualenv where both requirements files are
installed, then restart Claude Desktop.

## Direct tool use vs MCP

| | Direct tool use (today) | MCP server (this demo) |
|---|---|---|
| Where the tool schema lives | Hand-written dict in `agents/qualification.py`, can drift from the function | Generated by FastMCP from the function's signature and the description passed to `@mcp.tool` |
| Who runs the tool | The agent's own process, in-process, in its tool-use loop | A separate server process; the MCP client forwards calls over stdio |
| Reuse | Only code that imports and wires it up | Any MCP client (Claude Desktop, other agents) can use it without custom glue |
| Control over the loop | Full: custom error handling, retries, rate limiting (`call_claude`) | Client-defined; the host app drives the loop |
| Extra moving parts | None | A process, a transport, a client config |
| Token cost of the definition | See `results.json` after you run `measure_tokens.py` | Same |

## What this does not show

- **One tool only.** The tool-definition overhead of MCP versus direct tool
  use is only interesting at scale; with a single tool the token difference
  may be small, or none.
- **Local stdio only.** No remote transport, auth, or multi-user behavior.
- **Not production.** No rate limiting, logging, input validation beyond what
  `score_lead` already does, or deployment story. The live pipeline does not
  use this server.
- **Scoring only.** It does not show the agent's reasoning or tiering, only
  that the same function can be served over MCP.
